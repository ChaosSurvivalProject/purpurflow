## 1.2 双端网络 API 真实签名与所属包

### 【已证实】服务端（Bukkit/Paper/Purpur）

```java
// 包：org.bukkit.plugin.messaging
org.bukkit.plugin.messaging.Messenger
    .registerIncomingPluginChannel(Plugin plugin, String channel, PluginMessageListener listener);
    .registerOutgoingPluginChannel(Plugin plugin, String channel);
    .sendPluginMessage(Plugin source, String channel, byte[] message);   // Player#sendPluginMessage 等价
org.bukkit.plugin.messaging.PluginMessageEvent
    // onPluginMessageReceived(String channel, Player player, byte[] message)
```

- 通道命名规范：Bukkit 侧传统用 `namespace:channel`，长度约束来自 MC Identifier（命名空间 `[a-z0-9_.-]`）。本工程用 `purpurflow:main`。
- 来源：[Bukkit Messenger Javadoc](https://jd.papermc.io/paper/1.21.11/org/bukkit/plugin/messaging/Messenger.html)、[PluginMessageEvent](https://jd.papermc.io/paper/1.21.11/org/bukkit/plugin/messaging/PluginMessageEvent.html)。

### 【已证实】客户端（Fabric 1.20.5+ 新网络系统）

```java
// 注册 payload 类型（common 初始化，收发两端都要注册）
net.fabricmc.fabric.api.networking.v1.PayloadTypeRegistry
    .playS2C().register(CustomPacketPayload.Type, StreamCodec);
    .playC2S().register(CustomPacketPayload.Type, StreamCodec);
    .playS2C().registerLarge(Type, StreamCodec, int maxPacketSize); // 官方分包

// 标识与编解码
net.minecraft.network.protocol.common.custom.CustomPacketPayload;
net.minecraft.network.protocol.common.custom.CustomPacketPayload.Type;
net.minecraft.network.codec.StreamCodec;   // 1.20.5+ 取代旧 PacketCodec 成为主流

// 收发
net.fabricmc.fabric.api.networking.v1.ClientPlayNetworking
    .registerReceiver(Type, ClientPlayNetworking.PlayPayloadHandler);
    .send(CustomPacketPayload);
    .canSend(Type);                       // 能力探测：对端是否声明支持该通道
net.fabricmc.fabric.api.networking.v1.ServerPlayNetworking
    .registerReceiver(Type, ServerPlayNetworking.PlayPayloadHandler);
    .send(CustomPacketPayload, PacketTarget);
    .canSend(ServerPlayer, Type);
```

- `StreamCodec.composite(...)` 是构造复合 codec 的常用方式。
- **configuration phase 与 play phase 分离**：`PayloadTypeRegistry` 提供 `configurationS2C/C2S` 与 `playS2C/C2S` 四组；本工程增强流只在 **play 阶段**收发，configuration 阶段不做增强流（规避登录时序坑，见 04 文档）。
- **handler 所在线程**：Fabric 的 payload handler 在**主线程（netty 经网络线程转到主线程）**执行（NeoForge 文档亦印证 handler 有 MAIN/NETWORK 之分，Fabric 默认主线程）。因此 handler 内**禁止阻塞/重负载**，符合 H3/安全边界。
- 来源：[Fabric Networking 文档](https://docs.fabricmc.net/develop/networking/)、[PayloadTypeRegistry Javadoc](https://maven.fabricmc.net/docs/fabric-api-0.139.4+1.21.11/net/fabricmc/fabric/api/networking/v1/PayloadTypeRegistry.html)。

### 【工程建议】统一通道标识

双端共用同一个 `Identifier("purpurflow", "main")`，Fabric 侧 `Type` 与 Bukkit 侧 channel 字符串都由此派生，代理场景（Velocity/Bungee）只转发同名 plugin message，不新增链路。

## 1.3 字节上限与压缩

### 【已证实】custom payload 实际上限（上下行不对称！）

| 方向 | 上限 | 说明 |
|---|---|---|
| 下行 clientbound（server→client） | **1,048,576 B（1 MiB）** | 原版客户端对未知 channel 强制该长度上限 |
| 上行 serverbound（client→server） | **32,768 B（32 KiB）** | NeoForge/Fabric 文档一致，由 MC 包系统强制 |
| cookie_response 特殊通道 | 5 KiB (5120 B) | 与本工程无关，仅提示不要复用 cookie 通道 |

- 来源：[Minecraft Wiki - Java Edition protocol/Packets](https://minecraft.wiki/w/Java_Edition_protocol/Packets)、[NeoForge Custom Packet Payloads](https://deepwiki.com/neoforged/Documentation/6.1-custom-packet-payloads)。

**设计后果**：
1. 上行 `HELLO` / 能力位图 / ack 必须极简，远小于 32 KiB —— 天然满足。
2. 大消息只走下行；下行超过 1 MiB 时用 **Fabric 官方 `registerLarge`** 分包（已证实存在），上行超过 32 KiB 的自研分片（本工程尽量避免上行大消息）。
3. 分片上限**运行时探测**：Fabric 侧 `registerLarge` 的 `maxPacketSize` 在本工程锁定的 Fabric API `0.139.4+1.21.11` 中**只接受 `int`（固定上界），没有 `IntSupplier` 重载**（该重载是更高版本 Fabric API 才引入的）；故代码用 `int` 上界（见 `PayloadRegistrations.java`），真正的自适应分片在**自研 `Fragmenter` + 握手协商的 `HELLO_ACK.serverMaxChunk`** 处实现，不依赖 Fabric 动态重载。服务端侧从 `HELLO.localMaxChunk` 读取客户端声明值。**不硬编码业务上限**。（R-14 修正，原声明与锁定版本不符）

### 【已证实】原版连接压缩阈值

- 配置项 `network-compression-threshold`，位于 `server.properties`，默认 **256** 字节，`-1` 表示禁用，`0` 表示全压缩（不推荐）。
- 超过阈值的包由服务端用 zlib(DEFLATE) 压缩后发送，阈值由服务端在握手时通告客户端，两端共同遵守。
- 来源：[Minecraft server.properties 1.21 参考](https://survivalconfigs.com/reference/minecraft/server-properties)、[RE:NODE 网络阈值说明](https://renode.space/blog/minecraft-network-compression-threshold-and-packet-rate-limits)。

**设计后果**：原版链路已有压缩，因此本工程 L4 **默认不二次压缩**，先靠字典化 + delta 降熵；是否开启帧级压缩由 A/B 压测决定（见 03、06 文档）。

### 【已证实 / 需实测验证】PacketEvents 与 ProtocolLib

- **PacketEvents**：2.11.0（2025-12-09）起支持 1.21.11，之后持续维护（至 2.14.0，支持到 26.3），平台覆盖 Bukkit/Paper/Purpur/Fabric/Velocity 等，GPL-3.0。→ **【已证实】维护活跃，1.21.11 可用**。
  来源：[PacketEvents 博客](https://www.packetevents.com/blog)、[Modrinth](https://modrinth.com/plugin/HYKaKraK)。
- **ProtocolLib**：在 1.21.11 的具体最新稳定版本与维护节奏**未在本轮核实中直接确认** → **【需实测验证】**：部署前到其官方发布页核对 1.21.11 支持状态，运行时通过插件依赖检测 + 版本白名单做门控，不硬编码版本号。
- 两者都只用于可选的 **② 原版同步包拦截层**（默认关闭），不影响默认方案（纯官方 API）。

## 1.4 核实结论对设计的直接影响

| 事实 | 影响的设计点 |
|---|---|
| 上行仅 32 KiB、下行 1 MiB | §2.3 分片策略、§2.7 中 `HELLO` 极简化、`localMaxChunk` 能力位 |
| Fabric `registerLarge` 存在 | L1 帧层优先复用官方分包，减少自研分片风险（H1 不受影响，仍是同一连接） |
| 原版已有压缩阈值 256 | §2.6 压缩默认关闭，先字典+delta；A/B 压测口径 |
| handler 在主线程 | §2.8/H3 处理器禁止阻塞，队列/编解码放到网络线程侧 |
| 1.21.11 是最后混淆版 | 代码用 Mojang mappings，降低未来升级成本 |
| PacketEvents 活跃 | 可选增强层可作为合法依赖项；ProtocolLib 需运行时门控 |
