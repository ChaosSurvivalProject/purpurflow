# 04 · 稳定性四约束落地（第 2.8 阶段）

## H1 · 零额外端口 / 单连接复用（最高优先级）

**实现**：所有增强信息流 100% 复用玩家已建立的 Minecraft TCP 连接（play 阶段 custom payload / plugin message），上下行同链路。

**逐条对照禁止项自检**：

| 禁止项 | 本方案状态 | 说明 |
|---|---|---|
| 新建 `ServerSocket` | ✅ 无 | 代码库无 `ServerSocket` / `DatagramSocket` |
| 监听任何 TCP/UDP 端口 | ✅ 无 | 无 `bind` / `listen` |
| 内嵌 HTTP/WebSocket/gRPC/MQTT | ✅ 无 | 无相关依赖 |
| 独立中继进程 | ✅ 无 | 纯插件 + Mod |
| 客户端入站连接 / P2P / NAT 穿透 | ✅ 无 | 客户端只通过已连接连接收发 |
| Velocity/Bungee 新增监听端口 | ✅ 无 | 跨服只复用代理已有 plugin message 转发 |
| 任何跨进程端口通信 | ✅ 无 | 无本地 socket |

**允许调整的是已有连接参数**（压缩阈值 `network-compression-threshold`、写缓冲水位），不是新增通道。

**为什么本方案不需要任何额外端口**：custom payload 是 Minecraft 协议原生能力，客户端与服务端在握手的 play 阶段已建立的 TCP 连接上，通过 `ClientPlayNetworking` / `Messenger.sendPluginMessage` 发送 `purpurflow:main` 通道字节，协议栈已负责可靠性、加密、压缩与连接管理。我们只是在这条既有「管道」里塞入自己的帧，不新建任何东西。

## H2 · 原版客户端兼容

- 服务端在握手完成前**不得向该连接下发任何增强帧**。
- 探测机制：
  - 服务端通过握手 `HELLO` 是否到达判断对端是否装 Mod；未到达即视为 vanilla。
  - Fabric 客户端用 `canSend(Type)` 确认服务端是否声明支持该通道。
- 探测失败即静默降级为 vanilla 模式，**不产生额外定时重试流量**（`VanillaFallback` 关闭出站注册、不设定时任务）。
- **vanilla 客户端进服回归测试**是验收硬门槛（见 06 文档）。
- 需覆盖 configuration phase、登录时序、切服时的注册时机坑：本工程**只在 play 阶段注册与收发增强流**，configuration 阶段不做，规避登录时序；切服时重新走握手（新 session）。

## H3 · 背压与拥塞控制

**仅在 Netty channel `isWritable()` 且队列低于高水位时出队写**（`BackpressureGate`）。

实现要点：
- **按玩家独立队列**保证公平（`PerPlayerSession` 持有自己的队列）。
- **优先级**：控制帧 > 关键状态 > 可丢弃遥测（`Priority` 枚举 + `PriorityQueue`）。
- **队列超限**按优先级丢弃，可丢弃帧与脏位图合并，不排队重发。
- **速率上限**：基于心跳 RTT 与 ack 速率做简易 AIMD 速率上限（`RateLimiter`）。
- **超时熔断** → 降级为低频全量快照。
- **内存上界**：所有队列、缓冲、重组区都有大小上限。
- **接口契约**：`EgressGate.offer(player, frame, priority) -> boolean`，`false` = 背压丢弃，调用方必须处理（日志计数 + 合并脏位图）。

**注意 handler 线程**：Fabric payload handler 在主线程执行（01 文档已证实），因此重负载的编解码、队列操作放到网络线程侧，handler 内只做轻量分发。

## H4 · 重连状态补偿

- 服务端按 `session/epoch` 保存快照与**有限长度** seq 日志（`ResumeStore` + `SnapshotStore`）。
- `RESUME` 命中 → 增量补发 `DELTA(fromSeq)`；未命中或日志被裁剪 → 发 `FULL_SNAPSHOT`（字典化 + 可选压缩）。
- 补发走**低优先级队列**，不挤占实时流。
- 客户端按 `seq` 去重（`DedupWindow`）、按 key 版本号 **last-write-wins**，保证不重复应用。
- **状态变更幂等**：`Delta.apply` 对同一版本号重复应用无副作用。

## H5 · 版本握手校验

- **能力位图 + 协议版本白名单 + 字典版本**三重校验（`Capability` / `ProtocolWhitelist`）。
- 降级路径见 03 文档状态机图：降版本重试一次；仍不匹配 → `DISABLED`，该连接标记 vanilla，之后零增强流量。
- **绝不崩服、绝不踢人、绝不写脏 vanilla 连接**：所有异常分支捕获并转 `DISABLED`，不抛到主线程、不调用 kick。

## 三条稳定性约束的协同关系

```
   H5 握手 ──通过──→ H2 兼容探测 ──装Mod──→ 建立会话
     │不通过                                    │
     └──→ DISABLED(vanilla) ←── H2 未装Mod ─────┤
                                                 ▼
                                        稳态收发（H1 同连接）
                                                 │
                        ┌────────────────────────┼──────────────────────┐
                        ▼                        ▼                      ▼
                   H3 背压门控             H4 重连补偿            安全边界（2.9）
```

## 2.9 安全边界

- **单帧/单消息大小上限**：超限拒绝 + 安全计数。
- **反序列化白名单**：只认固定 schema 与白名单 type，禁止任意类型反序列化（无 Java 原生序列化）。
- **配额**：每玩家每秒字节数与包数配额。
- **处理器约束**：增强流处理器不得执行阻塞或重负载操作。
- **防放大**：小上行不得触发大下行洪泛（上行 `HELLO`/ack 不触发全量下发，除非显式 RESUME 命中）。
- **异常计数与日志降噪**：异常计数限流，避免日志刷屏。
